signals-app · integration note

signals-client-ts

What a standalone TypeScript client for the signals engine would be, why the portal and the Schwab app both want one, and exactly what code it would replace on each side.

The signals engine already speaks HTTP. signals serve boots a FastAPI app with four routes; every one of them returns the same typed SignalOutput the CLI prints and the MCP server hands to Claude. Nothing new needs building on the engine side.

What is missing is the other end. Right now, for the portal or the Schwab app to ask “what’s the signal on NVDA?”, someone writes a fetch call, hand-types the response shape into an interface, guesses at the error cases, and repeats all of that in the second app. signals-client-ts is that glue, written once.

Scope — read this first The signals API is deliberately local / CI / agent only (design doc §1.3, §6). This client talks to a signals serve running on the developer’s machine or in a CI job — it is not a client for a public internet service, because there isn’t one. Each app points at SIGNALS_API_URL=http://localhost:8000 in development.

§1What the package contains

One small, dependency-free module. No React, no framework coupling — just fetch and types, so it drops into a Next.js route handler, a server action, a script, or a test with equal ease.

ExportKindWhat it is
createSignalsClient(opts) fn Factory. Takes { baseUrl, fetch?, timeoutMs? }, returns a client object. baseUrl defaults to process.env.SIGNALS_API_URL.
client.analyze(symbol, opts?) fn → Promise<SignalOutput>. Wraps GET /signals/{symbol}. opts: { period?, noLlm? }.
client.backtest(symbol, opts?) fn → Promise<BacktestResult>. Wraps GET /backtest/{symbol}. opts: { period?, horizonDays? }.
client.history(symbol, opts?) fn → Promise<RunRecord[]>. Wraps GET /history/{symbol}. Rows already match the browser HistoryEntry shape.
client.health() fn → Promise<{ status: "ok" }>. Liveness probe for a dev-environment banner.
SignalOutput, Signal, Evidence, BacktestResult, RunRecord type Hand-kept in sync with src/signals_app/schemas/signal_output.py. One source of truth, checked in CI (see §4).
SignalsError, SymbolNotFoundError, InsufficientDataError, UpstreamUnavailableError type Thrown, not returned. Mirror the service’s domain exceptions and the route’s status codes (404 / 400 / 503).

§2How a call flows

The client is a translation layer, nothing more. A call goes through four steps, each one a thing the two apps would otherwise duplicate:

  1. Build the URL. analyze("nvda", { period: "6mo", noLlm: true }) becomes GET {baseUrl}/signals/NVDA?period=6mo&no_llm=true. Symbol is upper-cased; params are only appended when set.
  2. Fetch with a timeout. An AbortController caps the request at timeoutMs (default 15s) so a hung signals serve surfaces as an error, not a frozen request handler.
  3. Map the status. 404 → SymbolNotFoundError, 400 → InsufficientDataError (or a plain SignalsError for a bad period), 503 → UpstreamUnavailableError, anything else → SignalsError with the response body attached.
  4. Return the typed body. On 200, response.json() is returned as SignalOutput — no cast at the call site, no re-declared interface.

§3Usage — the same three examples on both apps

A. Portal — a route handler that returns a signal card’s data

nuwrrrld-portal/src/app/api/signal/[symbol]/route.ts

import { createSignalsClient, SymbolNotFoundError, UpstreamUnavailableError } from "@nuwrrrld/signals-client";
import { NextResponse } from "next/server";

const signals = createSignalsClient(); // baseUrl from SIGNALS_API_URL

export async function GET(_req: Request, { params }: { params: { symbol: string } }) {
  try {
    const out = await signals.analyze(params.symbol, { period: "3mo" });
    // out is SignalOutput — out.signal.direction, out.signal.confidence,
    // out.data_quality_score, out.code_version are all typed.
    return NextResponse.json(out);
  } catch (err) {
    if (err instanceof SymbolNotFoundError) return NextResponse.json({ error: "unknown symbol" }, { status: 404 });
    if (err instanceof UpstreamUnavailableError) return NextResponse.json({ error: "signals engine unavailable" }, { status: 503 });
    throw err;
  }
}

B. Schwab app — enrich a positions table with a backtest hit-rate

schwab-nu1/src/lib/enrich-positions.ts

import { createSignalsClient } from "@nuwrrrld/signals-client";

const signals = createSignalsClient({ timeoutMs: 30_000 }); // backtests are slower

export async function enrich(positions: { symbol: string }[]) {
  const rows = await Promise.allSettled(
    positions.map(async (p) => {
      const bt = await signals.backtest(p.symbol, { horizonDays: 20 });
      const strong = bt.by_strength.find((b) => b.key === "STRONG BULLISH");
      return { symbol: p.symbol, hitRate: strong?.hit_rate ?? null, n: strong?.total ?? 0 };
    }),
  );
  // one bad symbol never sinks the batch — Promise.allSettled + typed result
  return rows.map((r) => (r.status === "fulfilled" ? r.value : null)).filter(Boolean);
}

C. Either app — a dev-only health banner

const signals = createSignalsClient();

export async function signalsReachable(): Promise<boolean> {
  try { await signals.health(); return true; }
  catch { return false; } // show "run `signals serve` to enable signal cards"
}

    "ai_degraded": true,          // LLM skipped / failed → rule-based fallback

  "matrix": null,

§4Keeping the types honest

A hand-written TS mirror of a Python schema drifts. The client would ship one guard against that:

  • A CI check in signals-app that fetches GET /openapi.json from a booted signals serve and diffs the generated types against the checked-in types.ts. A mismatch fails the build, with the diff in the log.
  • A schema_version field is on every payload. The client can assert it matches the version it was built against and warn loudly on a mismatch at runtime, not just in CI.

§5The three places it could live

OptionSetup costDrift riskBest when
In signals-app
clients/typescript/		 Low. Portal & Schwab add it as a file: or git dependency. Lowest. Types version with the API in the same commit; the §4 CI check is right there. You want one source of truth and don’t mind the two apps depending on a subdir of the engine repo.
Copied into each app
src/lib/signals-client.ts		 Zero cross-repo setup. Highest. Two copies, no shared CI, silently diverge on the next schema change. Only for a quick spike you expect to delete.
Standalone repo
~/code/signals-client-ts		 Highest. New repo, its own release/publish flow, version bumps to coordinate. Low if the CI check runs against a pinned signals-app version. The client grows its own surface (caching, retries, a React hook) and earns independent ownership.

Recommendation

Start in signals-app at clients/typescript/. It has the lowest drift risk — the whole reason the client exists is to stop the portal and the Schwab app from each re-deriving the schema — and it needs no new repo or publish pipeline. Promote it to a standalone repo later if it grows a real surface of its own (retry policy, response cache, a useSignal() hook). Never copy it into both apps: that recreates the exact duplication this is meant to remove.

§6What each app does to adopt it

  1. Add the dependency — "@nuwrrrld/signals-client": "file:../signals-app/clients/typescript" (or a git URL).
  2. Set SIGNALS_API_URL=http://localhost:8000 in .env.local; document it in .env.example.
  3. Add one line to the dev instructions: “signal features need signals serve running in the signals-app checkout.”
  4. In CI where signal features are exercised, add a step that pip install -es signals-app and runs signals serve & before the app’s tests.

No app code changes beyond importing createSignalsClient where a signal is needed — and deleting whatever ad-hoc fetch + interface currently stands in for it.
